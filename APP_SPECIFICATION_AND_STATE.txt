--------------------------------------------------------------------------------
1. APPLICATION OVERVIEW & DOMAIN MODEL
--------------------------------------------------------------------------------
Pure Max Water Factory OS is an enterprise-grade industrial Enterprise Resource
Planning (ERP) and Operations Management System tailored for packaged sachet
water and bottled water production, distribution, fleet tracking, and financial
accounting.

Key Core Metrics & Calculation Logic:
- Outer Film Packaging Yield: 1 Outer Film Set produces exactly 50 Water Bundles.
  Formula: Total Bundles = (Outer Sets Purchased/Used * 50) - Remaining Loose Sachets.
- Packaging Roll Tracking: Weight in Kilograms (KG). Tracks roll load onto machines,
  depletion rate, and waste percentage.
- Net Profit Formula: Gross Sales - (Operating Expenses + Raw Material Purchases + Repairs + Fuel).
- Attendance & Daily Wage Matrix: Automated wage calculations based on role and
  location tier (Factory Plant vs Field Distribution).

--------------------------------------------------------------------------------
2. ROLE-BASED ACCESS CONTROL (RBAC) MATRIX
--------------------------------------------------------------------------------
The system supports strict tiered roles with runtime UI enforcement & route guards:

1. DEVELOPER (`developer`):
   - Full unrestricted root access across all modules.
   - Access to System Health, PostgreSQL Query Terminal (PgAdmin), Live Logs,
     Reset DB / Purge Mock Data, Custom Theme Editor, Error Diagnostics.

2. CEO / OWNER (`ceo`):
   - Executive dashboard, full financials, gross & net profits, revenue analytics.
   - Attendance reports, sales overview, production monitoring, audit logs.
   - Restricted from developer low-level system settings.

3. GENERAL MANAGER (`manager`):
   - Operations oversight: Production logging, Sales verification, Expense approvals,
     Attendance approvals, User role assignment, Fleet GPS tracking, Inventory control.

4. ASSISTANT / SECOND MANAGER (`second_manager`):
   - Operational delegate to Manager: Attendance approvals, Production logs,
     Stock checks, Fleet monitoring, Sales recording.

5. SALES PRODUCTION OFFICER / SALES MANAGER (`sales_manager`):
   - Dedicated Daily Sales Module (SalesDailyRecordsModule) with detailed credit/cash tracking.
   - Production bundle receipt verification, Customer debt collection, Sales summary reports.
   - Restricted from engineering raw equipment logs and developer settings.

6. PRODUCTION ENGINEER (`engineer`):
   - Production batch entry, Machine maintenance logs, Outer film & Roll inventory intake,
     Equipment inspection & water quality testing logs (TDS, pH, micron filters).
   - Restricted from financial profit margins and user management.

7. MACHINE OPERATOR (`operator`):
   - Line-level machine status reporting (Running, Idle, Breakdown, Reloading roll).
   - Bundle production counts, damaged bundle logging, roll reel change tracking.

8. TRICYCLE DELIVERY STAFF (`tricycle_staff`):
   - Field sales dispatch, mobile GPS broadcaster, customer cash collections,
     individual daily sales submissions, personal attendance check-in.
   - Hidden from global fleet map view (can broadcast own GPS location).

9. VAN DELIVERY STAFF (`van_staff`):
   - Bulk delivery routing, mobile GPS broadcaster, bulk wholesale sales receipts,
     personal attendance check-in.

10. GENERAL FACTORY STAFF (`staff`):
    - Personal attendance check-in/check-out, team chat & announcements, profile.

5. PREVIOUS CORRECTIONS & ARCHITECTURAL DECISIONS
--------------------------------------------------------------------------------
1. RBAC GPS Map Access:
   - Secured route guard in `App.tsx` so `tricycle_staff` and `van_staff` cannot view other vehicles' positions globally, while retaining background GPS broadcasting.
2. 24-Hour vs All-Time Dashboard Metrics:
   - Fixed bug where all-time sales were displayed under today's summary. Created distinct date filtering logic for current 24-hour transactions.
3. Mock Sales Purge Endpoint:
   - Created `DELETE /api/sales/mock` on the Express server and connected it with a double-confirmation modal in the Developer portal to easily flush demo data.
4. Z-Index Layering Standardization:
   - Fixed modal overlays colliding with sticky headers:
     * Header & Sidebar: `z-50`
     * Normal Modals & Dialogs: `z-[200]`
     * WebRTC Active Calls & Global Notifications: `z-[400]`
5. Dual Light/Dark Theme Contrast:
   - Added `text-slate-900 dark:text-white` across Production, Attendance, and Roll tracker modules to ensure crisp readability in both bright sunlight and dark factory environments.
6. Login Screen Dark Bottom Overlay (`LoginModal.tsx`):
   - Root cause: background `<img>` used static `h-[100vh]`/`w-[100vw]`, which does not
     track the real mobile visual viewport. When a mobile browser's address bar
     collapses/expands, `100vh` leaves a gap at the bottom that exposed the page's
     `bg-slate-950` wrapper underneath it, reading as a dark bottom "overlay/shadow".
   - Fix: switched the fixed background wrapper + image to `w-[100dvw] h-[100dvh]`
     with `object-fit: cover`, so the image is always truly full-bleed edge-to-edge
     on every device, and removed the now-redundant size classes on the `<img>` itself
     (`w-full h-full` inside the dvh-sized wrapper).
7. Password Reset OTP — Account-Takeover Vulnerability Closed (`server.ts`):
   - Root cause found: `POST /api/auth/request-reset` returned the raw 6-digit OTP
     `code` in the JSON response unconditionally (originally meant as a dev-only
     testing aid, but shipped live). `POST /api/auth/verify-code` matched a submitted
     code against ANY account's reset row (`WHERE code = X`), not the specific account
     identified by the caller. Together: anyone who knew a staff member's email /
     employee ID / phone could call request-reset, read the OTP straight out of the
     response, and immediately reset that person's password — full account takeover,
     no message interception needed.
   - Fix:
     * `request-reset` no longer returns the OTP to the client at all in normal
       operation. A `devOnlyCode` field is only ever included when
       `NODE_ENV !== 'production'` AND neither email nor WhatsApp delivery succeeded
       (so local dev without SMTP/WhatsApp configured can still test the flow).
     * `verify-code` now resolves the target user FIRST from `accountIdentifier`,
       then only accepts a code that was issued to that same user's email/phone —
       codes can no longer be redeemed against a different account.
     * Added an in-memory rate limiter (`otpVerifyAttempts` map in `server.ts`):
       5 failed attempts per identifier locks that identifier for 15 minutes
       (`OTP_MAX_ATTEMPTS` / `OTP_LOCKOUT_MS`). This is intentionally in-memory
       (no schema migration) since the app runs as a single Node process; it resets
       on server restart, which is an acceptable tradeoff for this deployment model.
8. WhatsApp Password Reset Channel — Actually Implemented (`server.ts`):
   - Root cause found: the login screen's "WhatsApp / SMS API" reset-channel option
     was cosmetic only. The backend always sent email regardless of the selected
     channel; nothing was ever dispatched via WhatsApp.
   - Fix: added `sendWhatsAppOtp()` in `server.ts`, which calls the official
     WhatsApp Cloud API (`https://graph.facebook.com/v20.0/{PHONE_NUMBER_ID}/messages`)
     when `WHATSAPP_API_TOKEN` and `WHATSAPP_PHONE_NUMBER_ID` env vars are configured.
     If they are not configured (nothing is set up yet), `request-reset` now
     transparently falls back to email and tells the user honestly in the response
     message that WhatsApp isn't available yet, rather than silently doing nothing.
   - STILL NEEDED FROM THE HUMAN OWNER: a Meta/WhatsApp Business Cloud API account,
     a verified phone number, and the two env vars above. Until those are set, the
     channel will keep falling back to email (by design, not a bug).
9. Fleet Dispatch Cash Reconciliation — Built End-to-End:
   - This was the real substance of "Bundle Dispatch & Cash Reconciliation" (Issue #3
     of the Aug 2026 12-issue spec). The Van/Tricycle dispatch UI already existed in
     `SalesDailyRecordsModule.tsx`, but a full data-flow trace found it was broken at
     every layer:
     a. UI only ever computed EXPECTED revenue (`sold * unitPrice`) — there was no
        field for what the driver actually handed in, so a shortfall could never be
        detected in the first place.
     b. `AppContext.tsx`'s `addSalesRecord()` explicitly whitelisted the fields it
        forwarded to `syncEngine.enqueue('sales_create', ...)` and silently dropped
        `vehicleNumber`, `loadedBundles`, `unsoldBundles`, `damagedLosses` before they
        ever reached the server.
     c. `POST /api/sales` in `server.ts` hardcoded every sale as
        `paymentStatus: 'Paid in Full'`, `amountPaidLe: total`, `balanceLe: 0` —
        it was structurally impossible to record a shortfall no matter what the
        client sent.
     d. `GET /api/sales` never returned vehicle/loaded/unsold/damaged/real-payment
        fields at all, and derived `category` by sniffing substrings out of
        `productType` (`.includes('Van')` / `.includes('Tricycle')`) — which also
        silently miscategorized 'Wholesale Orders' and 'Damaged Bundles' records
        as 'Factory Sales' after every page refresh (a second, unrelated real bug
        found via the same trace).
   - Fix (all four layers):
     * `src/db/schema.ts`: added `category`, `vehicleNumber`, `loadedBundles`,
       `unsoldBundles`, `damagedLosses` columns to `sales_records`.
       >>> REQUIRES RUNNING `npx drizzle-kit push` (from `src/db/drizzle.config.ts`)
       >>> AGAINST THE LIVE DATABASE BEFORE THIS DEPLOYS — see Section 7 below.
     * `server.ts` `POST /api/sales`: now accepts `data.amountPaidLe` (actual cash
       collected; defaults to `total` for record types with no reconciliation step),
       computes `balanceLe = total - amountPaidLe`, sets `paymentStatus` to
       `'Cash Shortfall'` when a Van/Tricycle dispatch comes back short, stores the
       new columns, and inserts a `MANAGER`-category notification (visible to
       Manager/Second Manager, and to Developer/CEO who see everything) whenever a
       shortfall is detected.
     * `server.ts` `GET /api/sales`: now returns `category` from the dedicated
       column (falling back to the old substring-sniffing only for legacy rows
       created before this column existed), plus `vehicleNumber`, `loadedBundles`,
       `unsoldBundles`, `damagedLosses`, `amountPaidLe`, `balanceLe`, real
       `paymentStatus`.
     * `AppContext.tsx` `addSalesRecord()`: stopped dropping the dispatch fields;
       now forwards `category`, `amountPaidLe`, `vehicleNumber`, `loadedBundles`,
       `unsoldBundles`, `damagedLosses` to the sync queue.
     * `src/types.ts` `SalesRecord`: added `amountPaidLe?`, `balanceLe?`,
       `paymentStatus?`.
     * `SalesDailyRecordsModule.tsx`: added an "Actual Cash Collected From Driver"
       input to both the Van and Tricycle dispatch modals (`vanCashCollected` /
       `triCashCollected` state, defaults to expected revenue if left blank), with
       a live red shortfall banner that appears the moment collected < expected.
     * `DashboardModule.tsx`: added a "Cash Shortfall Alerts" widget, visible to
       Manager/Second Manager/Developer, listing any Van/Tricycle dispatch with
       `balanceLe > 0`, sorted most-recent-first, with a running total shortfall.
   - Verified with `npx tsc --noEmit` (clean) after each layer. NOT yet verified
     against a live Postgres instance or in a running browser (no DB/browser
     available in the sandbox this was built in) — see Section 7, "Needs human
     verification" for exactly what to click-test.
